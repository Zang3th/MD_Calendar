# Architecture

Technical structure of the application. This document is binding for all code (see [AGENTS.md](../AGENTS.md#architecture)).

## Runtime

- Plain HTML, CSS and JavaScript, started by opening `MD_Calendar.html` from the local filesystem. No server and no CDN at runtime. The only network access is the [synchronization with Google](#synchronization-with-google), started by the user, and only `io/google.js` may use network APIs.
- The JavaScript is bundled: esbuild turns `app.js` and everything it imports into one classic script, `dist/app.js`. `dist/` is generated and not committed; `npm run build` creates it. The build uses `harness/build` from MD_Libs (`../MD_Libs`).
- The application version is kept only in `package.json`. `tools/build.js` passes it to the MD_Libs build as the constant `MDC_VERSION` (`define`); the header writes it into the version label and the watermark.
- When `dist/app.js` is missing, the page shows only a notice to run `npm ci` and `npm run build`.
- The same files run unchanged from an `https` origin, because the mobile phase hosts them (see [Mobile](Mobile.md)). Nothing may depend on `file://`.
- Fonts are loaded only through `@font-face`. A `<link rel="preload">` for a font needs CORS and is blocked under `file://`.
- File access uses the File System Access API (`showDirectoryPicker`). Supported browsers are therefore Chromium-based (Chrome, Edge).
- Production files are ES modules, but they share one global namespace, `window.MDCalendar`, instead of exporting: each module adds its member there. Only `app.js` imports production modules, once each, in the order domain, io, ui; it is the entry point of the bundle. Layer modules import nothing but the npm packages their layer allows (see [Production dependencies](#production-dependencies)).
- Code is typed with JSDoc and checked by TypeScript (`checkJs`, strict) through `jsconfig.json`.
- Transient application state is plain JavaScript data.

## Production dependencies

| Dependency | Use |
|---|---|
| SortableJS | Drag and drop of entries within a day, between days, and between days and the backlog. Supports touch. |
| MD_Libs | Build and shared application core, including dates (see [Systems from MD_Libs](#systems-from-md_libs)). |
| Plus Jakarta Sans | UI font, stored locally. |

SortableJS and MD_Libs are npm dependencies and are bundled into `dist/app.js`; SortableJS has an exact version, MD_Libs follows its `master`; SortableJS is imported as its UMD build `sortablejs/Sortable.min.js`, which `app.js` loads before the production modules. The font is stored under `vendor/fonts/`. These are the only production dependencies; adding another one needs the user's approval. Recurrence rules are implemented in the domain layer; no recurrence library is used.

## Layers

| Layer | Responsibility | Must not |
|---|---|---|
| `domain/` | Business rules and state transitions: day lists, moves, recurrence expansion, backlog, contacts, derived birthdays, search, ICS import into the calendar, the comparison and plan of the synchronization, undo actions. | Access the DOM, browser APIs, files, storage adapters or SortableJS. |
| `io/` | Storage adapters, Markdown parsing and serialization per file type, ICS and vCard conversion, the Google client (token and Calendar API). | Access the DOM. Parsers and serializers additionally must not access files or browser APIs. |
| `ui/` | Rendering of state, DOM events, SortableJS callbacks, panels, dialogs, notifications. | Contain business or persistence logic, or change persistent data without a domain operation. |
| `app.js` | Wires the layers together, owns startup, saving and external change handling. | Contain business rules. |

All file access goes through the [storage adapter](#storage-adapter). Every change to persistent data is an action in the [undo history](#undo-history).

SortableJS may be imported only in `ui/`. MD_Libs entry points follow the layers: `domain/` imports `@zang3th/md-libs/core`, `io/` also `/platform`, `ui/` also `/ui`; `app.js` imports any. Dates are day keys `YYYY-MM-DD` without time zones; arithmetic, ISO weeks and formatting come from MD_Libs `core/dates`, the day and month names from `domain/calendar.js`.

## Storage adapter

One small interface from MD_Libs `platform/storage`. Domain and UI never know which adapter is active.

| Operation | Contract |
|---|---|
| `list()` | Names of the calendar files present in the folder. |
| `read(name)` | File text and a version stamp; `null` for a missing file. |
| `stat(name)` | Current version stamp without reading the text; `null` for a missing file. |
| `write(name, text, expected)` | Writes only if the file still has the `expected` content and returns the new stamp. `expected` is `null` to create a file that must not exist yet. A mismatch fails with an `MDLStorageConflictError` that carries the current text and stamp (`null` for a deleted file). |

All writes run through one serialized write queue. Every adapter passes the storage contract of MD_Libs.

Until the mobile phase there is one adapter for a local folder (MD_Libs `storage.folder`, opened by `io/storage.js`). Its version stamp is the file's modification time and size. `io/storage.js` also remembers the handles of the five most recently opened folders in IndexedDB (see [Startup](#startup)) together with a copy of the start-card summary of their `MD_Calendar.json`, updated after each update of the file, opens only folders that hold `MD_Calendar.json` and keeps the device ID for that file in `localStorage`. `io/folder-state.js` defines its schema; `app.js` updates it through the adapter when a folder opens, after each save and during a synchronization, one update after another, with the fingerprints of the saved files (taken from the texts the session hands over with `saved`, so the folder is not read again). A failure there only warns (`MDC-203`); the calendar never depends on the file. The mobile phase adds a second adapter (see [Mobile](Mobile.md)).

## Saving

- Saving is explicit (`Ctrl+S` or the save control). There is no autosave and no draft recovery after a crash. The one exception is the synchronization, which saves its own local changes at its end (see [Synchronization with Google](#applying-and-saving)).
- Saving and external changes are MD_Libs `platform/session` with the folder adapter; `app.js` wires its events to the header, the notifications and the conflict notice.
- Every file tracks whether it has unsaved changes. Saving writes all changed files through a serialized write queue. `Calendar.md`, `Backlog.md` and `Contacts.md` are written; `Holidays.md` and `Config.md` are only read. `Contacts.md` is written last.
- When the latest move between the calendar and the backlog went into the backlog, `Backlog.md` is written first, otherwise `Calendar.md` (see [DataFormat](DataFormat.md#rules-for-the-calendar-file)). A missing file is created only when its content differs from an empty one.
- Every write checks the version first. A mismatch never overwrites silently; the user chooses between reloading and overwriting.
- Closing the page with unsaved changes triggers the browser's leave warning.

## External changes

While the page is visible, the stamps of loaded files are checked every two seconds and on every return to the page.

- A changed file without local changes is reloaded and a notification says so.
- A changed file with local changes leads to the reload-or-overwrite choice.
- A deleted file always leads to the reload-or-overwrite choice; it is never emptied silently.
- A changed stamp with unchanged content (a sync client touched the file) is no change and no conflict. While the stamp is unchanged, the content is read again at most every 30 seconds.
- Written files are read back once after saving, so that a change right after the write is found.
- No reload happens while the entry dialog is open.
- External changes are handled per file. A changed `Holidays.md` or `Config.md` is always reloaded.
- “Reload” applies the versions of `Calendar.md`, `Backlog.md` and `Contacts.md` last read from disk and discards all local changes. Every reload of a written file starts a new undo history.

## Undo history

- Every change to persistent data is one action with a label, an `undo` and a `redo` function, and the view state before and after. This covers calendar entries, backlog and contacts.
- An operation that touches several files, such as moving an entry from the backlog into the calendar, is one action.
- The history is capped by entry count and memory size.
- The history keeps to real changes. After every action it compares a fingerprint of the written files’ texts with the states on the current path; an action that returns the data to an earlier state drops the steps in between, so that a change and its reversal (checking off and on, moving and moving back, a label cycled back) leave no steps. Repeated edits of one field of one contact (a text field, a label cycled on) that follow each other directly are one step, unless the state between them was saved. Both are options of MD_Libs `core/history` (`fingerprint`, `coalesce`).
- The number of unsaved changes shown in the UI is the distance between the current history position and the position at the last save. When the data serializes to exactly the files on disk again (an entry moved up and back down), the current position becomes the saved one and the count is 0, as MD_Manager compares with the saved text. It survives trimming; when new actions discard a redo branch that contains the saved state, the discarded steps are added to the distance.
- Reloading a file starts a new history.

## Notifications

- Severities: info, warning, error. Info and warnings dismiss themselves after 7 seconds; errors stay until dismissed and offer copyable details.
- Every error carries a stable code with the prefix `MDC-`. `MDC-0xx` are startup errors, `MDC-1xx` opening the folder, `MDC-2xx` saving and file checks, `MDC-3xx` configuration, `MDC-4xx` the synchronization with Google.
- Unexpected errors and unhandled promise rejections are reported as errors.

## Synchronization with Google

The rules of the synchronization are in [Domain](Domain.md#synchronization-with-google), the dialog in [Shell](ui/Shell.md#sync-dialog), the stored state in [DataFormat](DataFormat.md#md_calendarjson). No production dependency is added: the app uses `fetch` and WebCrypto.

### Access

- The app authenticates as a Google service account with the key in `MD_Calendar.key.json`. It signs a JWT (RS256 through WebCrypto, `iss` the service account, scope `https://www.googleapis.com/auth/calendar.events`, one hour) and exchanges it at `https://oauth2.googleapis.com/token` for an access token. Access tokens live only in memory and are fetched again when they expire.
- The token endpoint and the Calendar API answer requests from `file://` (`Origin: null`) with `Access-Control-Allow-Origin: null`, and requests from an `https` origin likewise; no server and no sign-in flow is needed (tested 26.11.2026).
- The service account reaches only calendars shared with it. The user shares one dedicated calendar with it (“Make changes to events”).
- One request to the events list of the calendar checks the setup and starts every synchronization: it proves that the calendar is reachable, gives the access role (`writer` or `owner` is required) and the calendar's time zone.

### Calendar API

- Changes are read with `events.list` and `singleEvents=false`, together with the events listed in `sync.open` (read one by one), whose differences were left open last time.
- Where only the calendar changed, the merge view reads the event of each row to show its Google side. The first query pages through the whole calendar; its last page returns a sync token, kept in `sync.syncToken`. Every later query sends the token and receives only the events changed or deleted since, deleted ones as `cancelled`. A token cannot be combined with a time range, so events before the cutover date are dropped locally. When Google rejects the token (HTTP 410), the app drops it, runs one full query and says so in the dialog.
- Events are created with the sync ID chosen by the app as the event ID, so a repeated create is answered with HTTP 409 and recognized as done instead of duplicated.
- Updates send the ETag from the check as `If-Match`; HTTP 412 means the event changed in Google since the check, and the difference stays open. Updates patch only the fields of [Domain](Domain.md#field-mapping).
- A delete that finds the event already gone (HTTP 404 or 410) counts as done.
- On HTTP 429 or 403 with a rate-limit reason the app waits as Google asks (or with an exponential backoff from 1s) and shows the countdown in the dialog.
- Local comparison runs in memory: the app parses nothing again, it fingerprints the synchronized fields of the loaded items and compares them with `sync.items`. Entries are compared field by field on both sides; a change in Google to an exported item (series, multi-day entry, day off) is recognized by a new ETag, of the event or of one of its occurrences. The comparison is `domain/sync.js`; it is pure and has no network access.

### Journal

“Apply” is a sequence of small transactions, one per difference:

1. Before the first request, the complete plan (operations, IDs, ETags, target states) is written as `sync.journal` into `MD_Calendar.json`.
2. The Google operations run one after another. Every operation is idempotent (IDs chosen in advance, `If-Match`, deletes that accept a missing event); after each one its state in the journal is updated in memory and the journal is written at least every 10 operations and before stopping.
3. The local changes of every difference that is done are applied as one undo action (`domain/sync-plan.js` builds the plan, runs it and turns it into that action), `Calendar.md` and `Backlog.md` are saved, `sync.items` takes the new states, `sync.last` and `devices.*.lastSynced` are set and the journal is removed, in one update of `MD_Calendar.json`.

“Cancel” lets the running operation finish and continues with step 3 for what is done. A journal found when a folder opens (a crash, a closed tab, a lost connection) means an interrupted synchronization: the sync control shows its warning state, and the sync dialog completes it by repeating the operations not recorded as done, which is safe because they are idempotent.

### Applying and saving

- “Check status” needs a saved state; the sync dialog saves through the normal save first (“Save and continue”, with the version check).
- The local changes are one action of the undo history. The synchronization saves them itself through the session's write queue with the version check; afterwards the unsaved count is 0. A version conflict while saving keeps the changes unsaved, keeps the journal open and shows the reload-or-overwrite choice; the next synchronization completes the journal.
- While the sync dialog is open, the automatic check for external changes waits; it resumes when the dialog closes, so that nothing is reloaded under a check or an “Apply”.

### Errors

| Code | Meaning |
|---|---|
| `MDC-401` | `MD_Calendar.key.json` missing, unreadable or not a service account key. |
| `MDC-402` | Google refused the token (key deleted or disabled in Google Cloud). |
| `MDC-403` | Calendar not found or not shared with the service account. |
| `MDC-404` | Calendar shared without write access. |
| `MDC-405` | No connection to Google. |
| `MDC-406` | Google rejected a request: a single operation (the difference stays open, the error is shown at its row) or the whole check (for example the Calendar API not enabled). |
| `MDC-407` | The sync state in `MD_Calendar.json` could not be written. |

Every error names the way out (share the calendar, replace the key, try again). Details never contain the key or an access token.

### One-time setup in Google Cloud

1. Open the Google Cloud console with the Google account of the calendar and create a project (for example “MD_Calendar”).
2. APIs & Services → Library: enable the **Google Calendar API**.
3. IAM & Admin → Service accounts: create a service account (no roles needed); its email address ends in `iam.gserviceaccount.com`.
4. On the service account, Keys → Add key → Create new key → JSON. The browser downloads the key file.
5. In Google Calendar on the web, create a new calendar (for example “MD_Calendar”). In its settings, under “Share with specific people”, add the service account's email address with “Make changes to events”. Under “Integrate calendar”, copy the calendar ID.
6. In MD_Calendar, open the sync dialog, pick the key file and paste the calendar ID. The dialog checks both and stores them.
7. On the phone, make the new calendar the default calendar of the Google Calendar app, so that new events land in it.

The key stays valid until it is deleted in Google Cloud; replacing it runs step 4 and 6 again. The one-writer assumption of [Product](Product.md#usage-profile) also covers the synchronization: one device synchronizes at a time.

## Startup

- Startup checks that the required browser APIs and resources (styles, font, logo) are present. A missing requirement blocks the app with a fatal notification instead of running in a broken state. A missing bundle is covered by the notice described in [Runtime](#runtime).
- The handles of the five most recently opened folders are kept in IndexedDB so that each can be reopened with one click from the start card. When the permission of the most recently opened folder is still granted, it opens automatically (see [Shell](ui/Shell.md#start-card)). A handle outlives its folder, so opening reads the folder first; a `NotFoundError` there means the folder is gone. A gone folder and a folder without `MD_Calendar.json` both leave the start card open with a warning instead of showing an empty calendar. Under `file://` Chrome asks for permission again in each session; that is accepted.
- Returning to the start card through the logo reloads the page and sets a flag in `sessionStorage` that keeps the next startup from opening the last folder. The flag is removed when it is read, and after two seconds when the reload was cancelled.

## Systems from MD_Libs

Shared systems come from MD_Libs (`../MD_Libs`, `@zang3th/md-libs`), the tested core shared with MD_Manager. MD_Calendar sets options and texts; it does not copy their code.

|---|---|---|
| Undo history | `core/history` | One history for all written files with a fingerprint of their texts; the unsaved count is its distance to the saved state. |

| Storage adapter, folder memory | `platform/storage`, `platform/handles` | Five recent folders with the cached summary (`update` keeps their order); `probe` tells a gone folder from a missing permission; `fingerprint` hashes saved files. |

| Search | `core/search` | Title, location, note and tag; diacritics ignored; every word must match. |
