# Architecture

Technical structure of the application. This document is binding for all code (see [AGENTS.md](../AGENTS.md#architecture)).

## Runtime

- Plain HTML, CSS and JavaScript, started by opening `MD_Calendar.html` from the local filesystem. No server and no CDN at runtime.
- The JavaScript is bundled: esbuild turns `app.js` and everything it imports into one classic script, `dist/app.js`. `dist/` is generated and not committed; `npm run build` creates it. The build uses `harness/build` from MD_Libs (`../MD_Libs`).
- When `dist/app.js` is missing, the page shows only a notice to run `npm ci` and `npm run build`.
- The same files run unchanged from an `https` origin, because the mobile phase hosts them (see [Mobile](Mobile.md)). Nothing may depend on `file://`.
- Fonts are loaded only through `@font-face`. A `<link rel="preload">` for a font needs CORS and is blocked under `file://`.
- File access uses the File System Access API (`showDirectoryPicker`). Supported browsers are therefore Chromium-based (Chrome, Edge).
- Production files are ES modules, but they share one global namespace, `window.MDCalendar`, instead of exporting: each module adds its member there. Only `app.js` imports production modules, once each, in the order domain, io, ui; it is the entry point of the bundle. Layer modules import nothing but the npm packages their layer allows (see [Production dependencies](#production-dependencies)).
- Code is typed with JSDoc and checked by TypeScript (`checkJs`, strict) through `jsconfig.json`.
- Transient application state is plain JavaScript data.

## Production dependencies

| Dependency | Use |
|---|---|
| SortableJS | Drag and drop of entries within a day, between days, and between days and the backlog. Supports touch. |
| MD_Libs | Build and shared application core, including dates (see [Systems from MD_Libs](#systems-from-md_libs)). |
| Plus Jakarta Sans | UI font, stored locally. |

SortableJS and MD_Libs are npm dependencies and are bundled into `dist/app.js`; SortableJS has an exact version, MD_Libs follows its `master`; SortableJS is imported as its UMD build `sortablejs/Sortable.min.js`, which `app.js` loads before the production modules. The font is stored under `vendor/fonts/`. These are the only production dependencies; adding another one needs the user's approval. Recurrence rules are implemented in the domain layer; no recurrence library is used.

## Layers

| Layer | Responsibility | Must not |
|---|---|---|
| `domain/` | Business rules and state transitions: day lists, moves, recurrence expansion, backlog, contacts, derived birthdays, search, ICS import into the calendar, undo actions. | Access the DOM, browser APIs, files, storage adapters or SortableJS. |
| `io/` | Storage adapters, Markdown parsing and serialization per file type, ICS and vCard conversion. | Access the DOM. Parsers and serializers additionally must not access files or browser APIs. |
| `ui/` | Rendering of state, DOM events, SortableJS callbacks, panels, dialogs, notifications. | Contain business or persistence logic, or change persistent data without a domain operation. |
| `app.js` | Wires the layers together, owns startup, saving and external change handling. | Contain business rules. |

All file access goes through the [storage adapter](#storage-adapter). Every change to persistent data is an action in the [undo history](#undo-history).

SortableJS may be imported only in `ui/`. MD_Libs entry points follow the layers: `domain/` imports `@zang3th/md-libs/core`, `io/` also `/platform`, `ui/` also `/ui`; `app.js` imports any. Dates are day keys `YYYY-MM-DD` without time zones; arithmetic, ISO weeks and formatting come from MD_Libs `core/dates`, the German day and month names from `domain/calendar.js`.

## Storage adapter

One small interface from MD_Libs `platform/storage`. Domain and UI never know which adapter is active.

| Operation | Contract |
|---|---|
| `list()` | Names of the calendar files present in the folder. |
| `read(name)` | File text and a version stamp; `null` for a missing file. |
| `stat(name)` | Current version stamp without reading the text; `null` for a missing file. |
| `write(name, text, expected)` | Writes only if the file still has the `expected` content and returns the new stamp. `expected` is `null` to create a file that must not exist yet. A mismatch fails with an `MDLStorageConflictError` that carries the current text and stamp (`null` for a deleted file). |

All writes run through one serialized write queue. Every adapter passes the storage contract of MD_Libs.

Until the mobile phase there is one adapter for a local folder (MD_Libs `storage.folder`, opened by `io/storage.js`). Its version stamp is the file's modification time and size. `io/storage.js` also remembers the last opened folder handle in IndexedDB (see [Startup](#startup)). The mobile phase adds a second adapter (see [Mobile](Mobile.md)).

## Saving

- Saving is explicit (`Ctrl+S` or the save control). There is no autosave and no draft recovery after a crash.
- Saving and external changes are MD_Libs `platform/session` with the folder adapter; `app.js` wires its events to the header, the notifications and the conflict notice.
- Every file tracks whether it has unsaved changes. Saving writes all changed files through a serialized write queue. `Calendar.md`, `Backlog.md` and `Contacts.md` are written; `Holidays.md` and `Config.md` are only read. `Contacts.md` is written last.
- When the latest move between the calendar and the backlog went into the backlog, `Backlog.md` is written first, otherwise `Calendar.md` (see [DataFormat](DataFormat.md#rules-for-the-calendar-file)). A missing file is created only when its content differs from an empty one.
- Every write checks the version first. A mismatch never overwrites silently; the user chooses between reloading and overwriting.
- Closing the page with unsaved changes triggers the browser's leave warning.

## External changes

While the page is visible, the stamps of loaded files are checked every two seconds and on every return to the page.

- A changed file without local changes is reloaded and a notification says so.
- A changed file with local changes leads to the reload-or-overwrite choice.
- A deleted file always leads to the reload-or-overwrite choice; it is never emptied silently.
- A changed stamp with unchanged content (a sync client touched the file) is no change and no conflict. While the stamp is unchanged, the content is read again at most every 30 seconds.
- Written files are read back once after saving, so that a change right after the write is found.
- No reload happens while the entry dialog is open.
- External changes are handled per file. A changed `Holidays.md` or `Config.md` is always reloaded.
- „Neu laden“ applies the versions of `Calendar.md`, `Backlog.md` and `Contacts.md` last read from disk and discards all local changes. Every reload of a written file starts a new undo history.

## Undo history

- Every change to persistent data is one action with a label, an `undo` and a `redo` function, and the view state before and after. This covers calendar entries, backlog and contacts.
- An operation that touches several files, such as moving an entry from the backlog into the calendar, is one action.
- The history is capped by entry count and memory size.
- The number of unsaved changes shown in the UI is the distance between the current history position and the position at the last save. When the data serializes to exactly the files on disk again (an entry moved up and back down), the current position becomes the saved one and the count is 0, as MD_Manager compares with the saved text. It survives trimming; when new actions discard a redo branch that contains the saved state, the discarded steps are added to the distance.
- Reloading a file starts a new history.

## Notifications

- Severities: info, warning, error. Info and warnings dismiss themselves after a few seconds; errors stay until dismissed and offer copyable details.
- Every error carries a stable code with the prefix `MDC-`. `MDC-0xx` are startup errors, `MDC-1xx` opening the folder, `MDC-2xx` saving and file checks, `MDC-3xx` configuration.
- Unexpected errors and unhandled promise rejections are reported as errors.

## Startup

- Startup checks that the required browser APIs and resources (styles, font, logo) are present. A missing requirement blocks the app with a fatal notification instead of running in a broken state. A missing bundle is covered by the notice described in [Runtime](#runtime).
- The last opened folder handle is kept in IndexedDB so the folder can be reopened with one click. When its permission is still granted, it opens automatically (see [Shell](ui/Shell.md#start-card)). Under `file://` Chrome asks for permission again in each session; that is accepted.

## Systems from MD_Libs

Shared systems come from MD_Libs (`../MD_Libs`, `@zang3th/md-libs`), the tested core shared with MD_Manager. MD_Calendar sets options and texts; it does not copy their code.

| System | MD_Libs | Use in MD_Calendar |
|---|---|---|
| Undo history | `core/history` | One history for all written files; the unsaved count is its distance to the saved state. |
| Save, undo and redo controls | `core/history` (`controls`) | German labels in `ui/header.js`. |
| Storage adapter, folder memory | `platform/storage`, `platform/handles` | One remembered folder. |
| Opening, saving, external changes, conflicts | `platform/session` | Reads all files on opening; several files, write order, automatic reload of unchanged files; checks every 2 s, on focus and on visibility, not while the dialog is open; asks before leaving with unsaved changes. |
| Startup checks | `platform/startup` | Styles, font and logo; codes `MDC-0xx`. |
| Search | `core/search` | Title, location, note and tag; diacritics ignored; every word must match. |
| Dates | `core/dates` | Day keys, weeks, the period a view shows, ISO week numbers, displayed dates with German names. |
| Line handling of the file formats | `core/markdown` | Byte order mark, line endings, trailing tags, `#Key` blocks; a warning for an unreadable character. |
| Notifications | `ui/notifications` | German texts, codes `MDC-`, action buttons, styled in `styles.css`. |
| Tooltips | `ui/tooltips` | No touch tooltips, keyboard focus only. |
| Completion sound | `platform/audio` | Plays the Arpeggio, which `app.js` defines. |
| Drag and drop | `ui/sortable` | SortableJS defaults and positions within day lists. |
| Keyboard shortcuts | `ui/keymap` | Bindings in `ui/interactions.js`; save works in text fields, everything else only without an open dialog. |
| Floating elements | `ui/popover` | The context menu at the pointer; tooltips; closing the context menu, help, holiday overview and search on an outside pointer and on Escape. |
| Build and harness | `harness/build`, `harness/testing`, `harness/checks`, `config/` | `tools/build.js`, unit-test bundles, the architecture checker, the icon test, `eslint.config.js`, the line count of `tools/project-stats.js` and the compiler options both jsconfig files extend. |
